# Fast Retro — QA / UX audit (2026-08-03)

Self-directed QA pass on the deployed test service (`fast-retro-sqlite-test`,
running commit `e4825a9`), driven through a real browser as a user would. Goal:
find bugs and UX rough edges. **Nothing here is fixed yet** — this is the
findings log for a later planning/fix pass.

Method: created boards, added cards, reacted, commented, voted, walked all five
phases, edited/deleted cards, ran the timer, ended + archived + started-next,
joined as a fresh non-lead participant, and drove it at a mobile viewport. Cross-
checked against the server logs, the SQLite DB, and the source.

Findings are ordered by rough severity. Severity is my judgment for a
trusted-team retro tool, not a formal risk rating.

---

## Bugs / issues

### 1. Idle WebSocket connections churn every \~33 seconds (no server keepalive) — Med

Every board connection disconnects and reconnects on a fixed \~33s cycle while
completely idle. Server log shows each socket living \~32.9s then a new one \~100ms
later, monotonically (`client 3 → 4 → 5 …`), i.e. one logical client reconnecting
over and over.

- **Root cause:** the y-websocket client (`frontend/src/lib/yboard.ts:26`) uses the
  default `messageReconnectTimeout` of 30s — it tears down the socket if it
  receives *nothing* from the server for 30s. The Rust WS server has no ping/pong
  or periodic keepalive (`grep ping/pong/keepalive src/*.rs` → none), so an idle
  board is silent and the client times out every cycle.
- **Impact:** constant reconnect churn — wasted CPU/log spam, worse battery on
  mobile, and presence/awareness can flap (users appear to leave/rejoin every
  33s). Each reconnect is a \~100ms offline gap; normally harmless thanks to CRDT
  resync, but it's the same connect-time code path as the sync races already
  fixed, so it's worth removing the churn entirely.
- **Fix direction:** send a server-side WebSocket ping (the reference Node
  y-websocket server pings \~every 30s), or a periodic no-op sync. The standard
  y-websocket server does this; this Rust reimplementation dropped it.

### 2. Lead/host status is stored only in localStorage — lost permanently if cleared / new device — Med

Boards created via "Start a new retro" store host status in a per-board
localStorage host key (`file boards.ts` `getHostKey`; server verifies `amHost`).

- **Confirmed:** clearing browser storage dropped me from lead → participant on my
  *own* board (`39jjzu`), with no way to reclaim it.
- **Impact:** clearing site data, switching browsers, or switching devices means
  you can never lead your own board again — no recovery/reclaim flow. The only
  durable lead path is the separate stable `/lead/<token>` URL.
- **Fix direction:** offer a recovery mechanism (e.g. show/export the host key, or
  a lead-token style URL for modal-created boards), or at least warn the user
  that host access is device-bound.

### 3. Live boards can't be deleted, resurrect from memory, and the dashboard grows unbounded — Med

- There is **no user-facing way to delete or close a live board.** The lead
  dashboard's "LIVE NOW" list only grows. It's currently cluttered with \~40
  boards including leftover `pw-*` / `qa-test-*` automation-test boards.
- **Deleted boards resurrect.** Boards deleted directly from the DB reappear
  because the server holds each Yjs doc in memory and re-persists it. (The two
  contaminated `test-2`/`test-3` boards deleted earlier today were both back in
  `board_docs` and still listed as LIVE NOW at the start of this session.)
- A contaminated board still displayed a stale label (`test-3` showing
  `test-2`'s name) — leftover in-memory state.
- **Fix direction:** add an explicit "delete/close board" action that evicts the
  in-memory doc and tombstones the slug so it can't re-persist; consider auto-
  archiving/expiring stale live boards. (Archives, by contrast, *are* deletable —
  see the archives page.)

### 4. Timer silently runs a 0:00 timer if you don't click "Set" first — Low-Med

The timer popover is `Minutes → [Set] → [Start/Pause/Reset]`. The natural flow
(type minutes, click Start) starts a **00:00** timer that does nothing, with no
feedback or warning. It only works if you click **Set** before **Start**
(verified: set 2 → Set → Start → counted down 02:00 → 01:58 correctly). Timer
expiry itself works and shows a clear "Time's up — wrap up your last point."
banner.

- **Fix direction:** apply the minutes field on Start, disable Start until a value
  is Set, or merge Set into Start.

### 5. "Lead-only" gating is UI-only; all board mutations are client-trusted — Low

Phase changes, rename, delete, anonymous toggle, etc. are Yjs-doc writes the WS
server just relays, with no field-level authorization. A participant could change
phase or delete cards by manipulating the client. Notably, **keyboard card-move
(Shift+arrows) isn't even phase- or lead-gated** — any participant can reorder /
move cards across columns anytime, while drag-merge *is* lead+group-gated in the
UI. Low severity for trusted-team use, but the enforcement is presentational, not
real.

### 6. Reaction picker has no vertical flip — opens off-screen for low cards — Low

The emoji picker is anchored `absolute top-full` (opens downward). There's a
horizontal viewport clamp (`pickerAlignRight`) but no vertical flip. For a card
near the bottom of the viewport the emoji grid renders below the fold and the
user must scroll to reach any emoji. (Reactions themselves work fine.)

### 7. Ended/archived boards still show a green "Live" dot — Low

After "Archive & end," the board is correctly read-only ("This retro has ended"),
but the header still renders the green "• Live" indicator next to the board name.
Cosmetic inconsistency.

### 8. Plain Enter doesn't submit a card (only ⌘/Ctrl+Enter) — Low

`Board.svelte:343` gates submit on `metaKey||ctrlKey`. The `⌘↵` hint is shown so
it's intentional, but many users reflexively press Enter and nothing happens.
Worth considering Enter=submit / Shift+Enter=newline.

### 9. Onboarding tip vs. reality: "click ▲ to upvote" but voting is disabled outside the Vote phase — Low

The first-run tips say "Click the ▲ on any card to upvote." A participant who
joins during Brainstorm and tries will find the upvote control greyed out
("Voting closed") until the lead reaches the Vote phase. Minor copy/expectation
mismatch.

### 10. Informational limits / hardening notes

- **No max card length** — a 3000-char card was accepted (clamped visually with
  "Show more"). Unbounded input.
- **No per-user vote budget** — voting is one toggle per user per card but
  unlimited across cards. Many retro tools cap votes (e.g. 3–5/person); this is a
  deliberate-looking design choice, flagging in case a cap is wanted.
- **CSV has no formula-injection guard** — escaping is RFC-4180 correct
  (commas/quotes/newlines handled in `file csv.ts`), but a card like `=SUM(A1)` exports
  verbatim and executes as a formula when opened in Excel/Sheets.

## Verified working well (not bugs)

- **XSS-safe:** card text like `<img src=x onerror=…>` renders as literal text; no
  script execution, page title untouched.
- **Comments** post and persist.
- **Reactions** add/remove and show counts (functionally fine; only the picker
  placement in #6 is an issue).
- **Voting** toggles correctly, one vote per user per card.
- **Edit / delete** work; delete has a "Delete this card?" confirm step.
- **End → Archive → Start next retro:** archive is saved, board goes read-only, and
  the new board comes up **empty** — the prior "stale cards on next retro" fix
  holds.
- **Archives page** (`/lead/<token>/archives`) lists snapshots, long previews are
  CSS-truncated (no layout blowout), and archives *are* deletable.
- **Non-lead participant view** correctly hides every lead control (End retro,
  Anonymous, phase advance, CSV, rename, Host badge).
- **Keyboard card-move** (Shift+↑↓←→) works for reorder and cross-column move.
- **Mobile viewport (390×844):** columns stack, phase strip wraps, hamburger menu
  neatly holds all lead controls, banners adapt. Solid responsive design.
- **Docs / user guide** (`/docs`) has participant/lead tabs and reads well.
- **Server error log is clean** — no runtime errors during the whole session.

## Round 2 — multiplayer (two live participants, Alice + Bob)

Follow-up pass covering the collaboration features that the first round only
exercised solo. Ran two fully independent browser sessions on the same board.
**All of the following work correctly — no new bugs found:**

- **Real-time card sync:** Alice adds a card → Bob sees it within \~1s, and vice
  versa. Server round-trip only (BroadcastChannel is disabled), so this is true
  cross-device sync.
- **Presence:** both sides show "1 other online" with the correct other name
  (Alice sees Bob, Bob sees Alice).
- **Anonymous mode:** Alice (lead) toggles it and it applies live to both.
  Correct nuance — others' cards show "Anonymous", your own shows "you (hidden)"
  so you can still find your cards while their authorship is hidden to others.
- **Drag-merge (Group phase):** confirmed functional. (agent-browser's synthetic
  mouse-drag can't produce HTML5 drag events, so this needed real `DragEvent`s to
  drive — worth noting for any future automated e2e coverage: Playwright's
  `dragTo` / manual dispatch is required, not mouse move/up.) The merge unions
  votes, dedupes reactions, appends comments, concatenates text with a `— — —`
  divider, deletes the source card (no data loss), and **syncs to the other
  participant**.
- **Vote aggregation:** Alice and Bob both upvote the same card → both see a
  combined count of 2, each showing their own "Remove vote" state.

Net: the multiplayer/CRDT layer itself is in good shape. The issues from Round 1
stand on their own (WS keepalive churn, localStorage-only host, board lifecycle,
etc.) and none were caused by concurrency.
